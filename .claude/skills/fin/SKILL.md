# /fin — 작업 마무리 (검증 → 작업보고서 → 커밋 → 푸시)

사용자가 `/fin`을 입력했을 때 이번 세션의 작업을 마무리한다. 추가 인자가 있으면 커밋 메시지·보고서 제목의 힌트로 쓴다.

## 1. 변경 사항 파악

- 저장소 루트(`self-layer/`)에서 `git status --short`, `git diff --stat`, `git diff`(staged 포함)를 확인한다.
- 이번 대화에서 한 작업과 실제 변경 파일을 대조해 작업 목적과 변경 내용을 정리한다.
- 커밋에서 **제외**할 것: `.env*` 등 비밀값 파일, `test-results/`, `playwright-report/`, `.next/`, 임시 파일. `.gitignore`에 없는데 비밀값처럼 보이는 파일이 있으면 커밋하지 말고 사용자에게 알린다.
- `project_sources/`의 새 원본 자료는 저장소가 함께 관리하므로 포함한다. 단 기존 원본 파일이 **수정**되어 있으면 멈추고 사용자에게 확인한다(원본은 읽기 전용).
- 변경 사항이 없으면 그렇게 알리고 끝낸다.

## 2. 검증 실행

`my-app/`에서 실행하고 실제 결과를 기록한다.

```powershell
npm.cmd run lint
npm.cmd run typecheck
npm.cmd test
npm.cmd run test:e2e   # UI·흐름을 바꾼 작업이면 실행
```

- Next 16은 한 프로젝트에 개발 서버를 하나만 허용한다. 사용자가 `npm run dev`를 켜 둔 상태면 E2E 서버가 "Another next dev server is already running"으로 실패하므로, 켜 둔 서버를 끄지 말고 `E2E_BASE_URL=http://localhost:3000`을 주고 실행한다.

- 실패하면 커밋하지 않는다. 원인을 사용자에게 보고하고 수정할지 묻는다.
- 실행하지 않은 검증은 보고서에 "실행하지 않음"과 이유를 적는다. 통과했다고 쓰지 않는다.

## 3. 작업보고서 작성

`my-app/docs/work/README.md`의 규칙과 형식을 따른다.

- 경로: `my-app/docs/work/YYYY-MM-DD.md`. 날짜는 **Asia/Seoul 기준 오늘**이다(`TZ=Asia/Seoul date +%F`로 확인).
- 같은 날짜 파일이 있으면 기존 내용을 보존하고 `## 작업 N: 작업명`으로 이어 붙인다(N은 기존 마지막 번호 + 1). 없으면 `# YYYY-MM-DD 작업보고서`로 새로 만든다.
- 항목: 작업 목적 / 주요 변경 사항(관련 파일 경로와 무엇을 왜 바꿨는지) / 검증 결과(2단계의 실제 결과, 테스트 개수 포함) / 미완료 사항 및 다음 작업.
- 한국어로, 사실만 쓴다. 이번 보고서가 들어갈 커밋의 해시는 미리 적지 않는다.

## 4. 커밋

- 커밋은 현재 브랜치에 한다. 관련 파일을 경로를 지정해 스테이징한다(`git add -A`로 비밀값이 섞이지 않게 1단계 목록을 기준으로 한다).
- 메시지 형식: `<type>: <요약>` (type은 feat / fix / refactor / docs / test / chore). 본문에 주요 변경을 몇 줄로 적는다. 사용자 지침이나 시스템이 지정한 공동 작성자 줄이 있으면 마지막에 붙인다.
- 훅이 실패하면 `--no-verify`로 우회하지 말고 원인을 고친 뒤 새 커밋으로 다시 시도한다.

## 5. 푸시

- `git push origin <현재 브랜치>`. 업스트림이 없으면 `-u`를 붙인다.
- 원격이 앞서 있어 거부되면 **강제 푸시하지 않는다.** 상황을 알리고 `pull --rebase` 여부를 사용자에게 묻는다.

## 6. 보고

사용자에게 다음을 짧게 알린다: 커밋 해시와 메시지, 푸시한 브랜치, 보고서 파일 경로, 검증 결과 요약, 제외한 파일이 있으면 그 목록과 이유.
